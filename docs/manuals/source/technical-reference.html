1.3 Design principles

  • Single decision point. Every access decision is made by AccessDecisionService in UMS. AMS contains no role checks; it describes the action and the record to UMS and acts only on an Allow.
  • Fail closed. An unreachable UMS, a missing attribute or an ended session never results in access.
  • Clean architecture / SOLID. Dependencies point inwards (Presentation → Infrastructure → Application → Domain). Use cases depend on interfaces only. Each class has one reason to change (for example sender, template, resolver and recipient policy are separate e-mail classes).
  • Tenant isolation. The tenant always comes from the signed-in user's token, never from a request body.
  • Explainability. Every decision carries the step that decided it and a human-readable reason, shown to users and written to the user action trail.

3Identity, sign-in and sessions (UMS)

3.1 Sign-in (L-01, L-02)

POST /api/v1/auth/login with email, password, appCode, clientIp, userAgent. The handler runs these steps in order; the first failure ends the request.

  1. Lockout check. Load the LoginAttempt for the login name. If LockedUntil is in the future → auth.locked ("Try again after hh:mm").
  2. Password check. Find the user by e-mail and verify the PBKDF2 hash. On failure, count the failure (L-07). If the count reaches MaxFailedLogins the login locks for LockoutMinutes → auth.locked, otherwise auth.invalid. Unknown e-mail and wrong password give the same answer (no account enumeration).
  3. Account check. The tenant must be active and the user usable today (status Active, account expiry not passed) → otherwise auth.disabled.
  4. Application check. appCode (default UMS) must be registered and enabled for the user's tenant → otherwise auth.app.
  5. Reset the failure counter.
  6. Single-device login. If SingleDeviceLogin is on, every open session of the user in the same application is ended with reason Replaced, and its validator cache entry is cleared.
  7. Create the session (UserSession): id, tenant, user, emp code, app, IP, user agent (max 300 chars), ExpiresAt = now + RefreshTokenDays, LastSeenAt = now, refresh-token hash.
  8. Record the last login and a user action log entry ({APP}.SESSION.SIGN_IN, "session on another device was ended" when L-02 applied).
  9. Issue tokens (L-03) and return LoginResultDto: access token and expiry, refresh token, session expiry, session id, user id, tenant id, name, e-mail, emp code, app code, idle timeout minutes, EndedOtherSessions.

3.2 Access tokens (L-03)

HS256 JWT, lifetime JwtExpiryMinutes (default 15), issuer and audience from Jwt:*; the key must be at least 32 bytes (checked at start-up). Claims:

ClaimMeaning
sub / name identifierUser id
sidSign-in session id. Every request is checked against this session (L-05).
appApplication the session belongs to (AMS.Api accepts only AMS).
tenant_id, emp_code, name, e-mailIdentity of the caller, used for tenant isolation and audit.
jtiUnique token id.

3.3 Refresh and reuse detection (L-04)

A refresh token has the form {sessionId:N}.{random}; only its SHA-256 hash is stored. POST /api/v1/auth/refresh:

  1. Parse the session id; unknown session → session.expired.
  2. Compute the session status (ended, expired, idle). If not active → end it (if not already) and return session.<reason>.
  3. If the presented token does not match the current hash, it is an old token (already rotated): someone may hold a copy, so the whole session ends with TokenReuse.
  4. The user and tenant must still be usable → otherwise AccountDisabled.
  5. Rotate: new refresh token, store its hash, clear the validator cache, issue a new access token.

3.4 Session validation on every request (L-05)

JWT bearer authentication in the UMS API has an OnTokenValidated hook:

  • No sid claim → fail ("token is not bound to a sign-in session").
  • ISessionValidator.CheckAsync(sid) loads the session and the tenant's idle timeout. The result is cached for 10 seconds per session, and the cache entry is cleared whenever UMS ends or rotates the session.
  • Status order: ended → its reason; now ≥ ExpiresAt → Expired; now − LastSeenAt > idle → Idle; otherwise active.
  • If the session ran out but is not yet recorded as ended, the validator records the end (reason and time). The admin's Active Sessions page and the audit then show it.
  • Not active → authentication fails; OnChallenge adds the header X-Session-End: <Reason>, which CORS exposes to browsers.

3.5 Status, keep-alive, logout and revoke (L-06)

3.6 Lockout (L-07)

LoginAttempt(Login, FailedCount, LockedUntil). RegisterFailure(now, max, lockout) increments the count; when it reaches max, LockedUntil = now + lockout and the count resets. A successful sign-in clears it. Attempts are keyed by login name, so locking works for unknown names too.

4Authorisation engine (UMS)

4.1 Decision layers (L-08)

AccessDecisionService.Decide(request, context) answers: can user U perform action A on record R in module M of application P, now, from this network, device and channel? Layers run in order. The first failing layer denies (deny-overrides), and every layer adds an explanation step.

#LayerPasses whenExample deny reason
1TenantTenant exists and is activetenant … is inactive
2IdentityUser active and not past account expiryaccount expired on 2027-03-31
3ApplicationApp registered, active, enabled for the tenant, and some active role grants APP.*.*.* or more specificno role grants access to Finance ERP
4ModuleA role grants something in the moduleno permission on module Reports
5Resource · ActionResource exists, action valid for it, and a role grants the exact keymissing POS.BILLING.INVOICE.REFUND
6ScopeAt least one granting role assignment is in scope for the recordlocation: role scoped to 'HO-GGN', resource is 'S045'
7PoliciesEvery applicable Restrict holds and no applicable Deny matchesDeny 'Supervisor refund limit ₹10,000' — resource.amount (15000) > '10000'

In layers 3–6 an applicable Grant policy whose conditions hold can stand in for a missing role permission (e.g. "employees see assets issued to them"). Restrict and Deny policies still apply afterwards.

4.2 Permission keys (L-09)

APP.MODULE.RESOURCE.ACTION, upper-case. Each segment may be *. A role grants a key if any of its patterns matches segment by segment: AMS.*.*.* grants every AMS action, *.*.*.VIEW every view. Actions: View, Create, Edit, Delete, Approve, Export, Print, Void, Refund, Checkout, Checkin, Audit, Request. A resource declares which actions are valid for it; an action the resource does not declare is denied at layer 5.

4.3 Role validity and scope (L-10)

  • Validity. An assignment counts only if the role is active and ValidFrom ≤ today ≤ ValidTo (open-ended when empty). Example: Rahul's temporary Procurement Head role is ignored after 10 Oct 2026.
  • Scope. An assignment may carry a scope, e.g. {"location": "HO-GGN"} or {"store": "S045,S046"} (comma = any of). For every scope key that the record carries, the record's value must be one of the listed values (case-insensitive). Keys the record does not carry do not restrict, so licences (no location) are visible to a location-scoped manager.
  • If any granting assignment is in scope, layer 6 passes. If only scoped assignments grant the key and none is in scope, a Grant policy can still allow; otherwise deny with the mismatch.

4.4 Policies (L-11)

  • A policy targets app / module / resource / actions (each may be *), optionally only users holding certain roles.
  • Applicable policies are evaluated in Priority order (lower number first).
  • Restrict: conditions must be true, else deny. Deny: if conditions are true, deny. Grant: if conditions are true, allow without a role permission.
  • Conditions combine with All (AND) or Any (OR).

4.5 Conditions and attribute context (L-12)

The engine builds a context dictionary for each request:

PrefixAttributes
user.*id, empCode, department, designation, location, region, employmentType, mfaEnabled, roles (comma list) + custom user attributes (e.g. vendorCode)
resource.*app, module, type + every attribute the application sends for the record (store, amount, cost, location, ownerEmpCode…)
env.*date, time, day, ip, network, device, channel, isHoliday; env.now for schedule operators
actionThe requested action

Operators: == != in "not in" > >= < <= contains "starts with" "within schedule" "outside schedule", all case-insensitive. Numbers are compared numerically, otherwise as text. The right-hand side may be a literal or another attribute (resource.store == user.location). A missing attribute never satisfies a condition, so a Restrict fails and a Deny or Grant does not match: fail closed.

4.6 Office hours and holidays (L-13)

A schedule has a time zone (Asia/Kolkata) and weekly windows such as Mon–Sat 09:30–18:30. A window whose end is before its start runs overnight (22:00–06:00: after-midnight times belong to the previous day's window). If the schedule excludes holidays, a holiday for the tenant closes it; holidays may be all-India or limited to regions, matched against the user's region.

4.8 UMS protects itself (L-15, L-16)

  • Each admin endpoint carries [RequirePermission(module, resource, action)]. The filter asks the same engine about the caller for UMS.<module>.<resource>.<action> and returns 403 with the reason when denied.
  • Security:RequireAuthentication = false skips this filter. It is meant only for local demos and is true by default.
  • The tenant of a request comes from the X-Tenant-Id header, else the tenant_id claim. Only an active SUPER_ADMIN may work in another tenant.

6AMS web portal: authentication and session handling

6.1 Sign-in hand-off (L-19)

Blazor Server runs over a WebSocket, which cannot set cookies. The portal therefore signs in in two steps:

  1. The sign-in page calls UMS auth/login (app AMS, browser IP and user agent) from the server.
  2. On success the tokens go into the server-side token store (L-20), and a single-use ticket (valid 60 seconds, in memory) is created.
  3. The page posts a hidden form with the ticket and an antiforgery token to POST /account/complete-login.
  4. That endpoint redeems the ticket and writes the HTTP-only cookie: __Host-AMS.Auth, Secure, SameSite=Lax, 60 minutes sliding, 12 hours absolute. Then it redirects to the return URL (local URLs only).

The cookie contains only the identity and the session id; UMS tokens never reach the browser.

6.2 Token store (L-20)

  • Holds per session id: access token and expiry, refresh token.
  • An access token within 60 s of expiry is refreshed through UMS. Refreshes are serialised per session (one refresh at a time, then double-checked), so parallel API calls do not trigger token-reuse detection.
  • When UMS refuses a refresh, the reason is recorded in EndedSessions (kept 13 h) and the tokens are dropped.

6.3 Checks while the user works (L-21, L-22)

6.4 Idle timeout (L-23)

  • The timeout is the tenant's SessionTimeoutMinutes, carried in the sign-in.
  • idle-timeout.js listens for pointer, key, wheel, scroll and touch events. It reports activity to the server at most every 10 s, and shares it between tabs through localStorage.
  • While the user is active it calls POST /account/keepalive every timeout/4, clamped to 30 s–5 min. This renews the cookie and calls UMS auth/session?touch=true.
  • The monitor ticks every second. At one minute left it shows the warning with a countdown; at zero it signs out with reason idle.

6.5 Sign-out and session-end routing (L-24)

  • POST /account/sign-out requires an antiforgery token, so a link or image on another site cannot sign users out.
  • It records the end, calls UMS auth/logout for signedout and idle (UMS already knows the other reasons), drops the tokens, clears the cookie, sends Clear-Site-Data: "cache", and redirects to the sign-in page with ?reason=.
  • If a page becomes anonymous because the session ended, RedirectToLogin routes through the sign-out page, so the cookie is cleared and an idle session is closed in UMS.
  • The sign-in page translates the reason into a message: replaced, idle, revokedbyadmin, tokenreuse, accountdisabled, expired, signedout.

7AMS API: request handling

7.1 API call service (L-25)

The portal reaches the API only through IAPICall.CallingAPI<TRes,TReq>(apiName, request):

  • The route comes from AmsApi:Routes[apiName], default api/v1/{apiName}. Names are constants in AmsApiNames, e.g. GET_ASSETS = GetAssets.
  • It sends POST with a JSON body (property names as in C#, enums as strings), Authorization: Bearer <fresh UMS token> and X-Client-IP.
  • A JSON BaseResponse is returned as is, for success and for refusals. A 401 also calls SessionEnded(X-Session-End).
  • It never throws to pages. Transport, timeout and JSON errors become responseCode = 1004 with a message; no token gives 401 without calling.

7.2 JWT validation and current actor (L-26)

  • Validation. AMS.Api validates the UMS token locally: issuer, audience, signing key, lifetime (30 s clock skew). It then requires app == AMS and a sid. A UMS-admin token is therefore rejected.
  • Current actor. HttpCurrentActor builds the Actor (user id, tenant, emp code, name, e-mail) from the claims and keeps the bearer token for calls to UMS.
  • Client IP. X-Client-IP is trusted only from configured forwarders (loopback plus Ums:TrustedForwarders). Otherwise the connection address is used.

8AMS use cases (business logic)

8.1 Guard and filtering (L-28 – L-31)

  • UmsAccessGuard.EnsureAsync(check) calls UMS me/authorize with the user's own token and the environment:
    • IP;
    • network: Office LAN for loopback and private addresses (10/8, 172.16/12, 192.168/16, IPv6 site and link local, fc00::/7), else Internet;
    • device and channel, from configuration.
    A deny throws AccessDeniedException with UMS's reason. UMS 401 becomes SessionEndedException; any other UMS failure becomes AuthorizationUnavailableException (fail closed).
  • FilterAsync keeps the items whose View check UMS allows, in one batch call. MatrixAsync asks for N items × K actions in one batch and returns a bool grid; it fills the Can* flags of each row.
  • Capabilities (GetCapabilities) are type-level checks of every module/resource/action, used for the menu and the page buttons. They only shape the UI; each action is checked again with the record's attributes.
  • Record attributes (ResourceAttrs):
    • asset: assetTag, cost, requestable, location, region, category, status, statusType, department, assignedToEmpCode;
    • check-out adds assigneeEmpCode, assigneeEmploymentType, assigneeDepartment, assigneeLocation, assigneeRegion;
    • request adds requestedByEmpCode and requestStatus;
    • maintenance: cost (job) and assetCost;
    • stock: cost = unit cost × quantity, and quantity;
    • licence: cost, seats, category, manufacturer.

8.4 Licences (L-34) and stock (L-35)

  • Licence:
    • seats ≥ 1, and seats cannot be reduced below the number in use;
    • a seat goes to a person and/or an asset; one seat per person per licence;
    • no check-out when all seats are used or the licence has expired;
    • deleting requires all seats checked in;
    • the product key is returned only when the caller may edit the licence.
  • Stock kinds map to separate catalogue entries (ACCESSORIES / CONSUMABLES / COMPONENTS):
    • Accessory: to a person, one each, returnable.
    • Consumable: to a person, quantity ≤ available, reduces stock, not returnable.
    • Component: into an asset, returnable.
    Quantity cannot drop below the units out; delete requires all units in; the kind of an item cannot change. Low = available ≤ minimum quantity.

8.5 Reports (L-36) and CSV (L-37)

  • Depreciation (straight line):
    • months = whole months since purchase;
    • value = cost × max(0, 1 − months / category life), rounded to paise;
    • a category life of 0 means no depreciation.
  • Due lists:
    • audits due: next audit within 30 days;
    • warranty ending: warranty end within the next 90 days;
    • overdue: checked out with an expected check-in date before today;
    • licences expiring (digest): within 30 days.
  • Dashboard and reports cover only the assets the caller may view (the same filter as lists).
  • CSV:
    • cells starting with = + - @ get a leading apostrophe (formula-injection protection);
    • cells containing a comma, quote or newline are quoted;
    • the file is UTF-8 with a BOM, for Excel.

9AMS data layer: Dapper and stored procedures (L-38, L-39)

  • DapperHelper:
    • opens a connection per call and runs a stored procedure;
    • logs queries slower than 3 s and SQL errors with the procedure name and parameters (secrets masked), then rethrows;
    • methods: ListAsync, SingleAsync, MultipleAsync (several result sets), WriteAsync, ExecuteBatchAsync.
  • Write contract. Every write procedure has outputs @Error_Code INT, @Error_Message NVARCHAR and, when inserting, @Record_Id. 0 = success, 1001 = not found, 1002 = rule violation, 1003 = duplicate. DbResult.EnsureOk() turns a failure into an AmsException with the same code.
  • Tenant isolation. Every table has TenantId; every procedure takes @TenantId from the token. A row of another tenant is "not found".
  • Audit fields. Writes receive @ActorEmpCode, @ActorName and @Now (IST business time) and add a History row (item type, id, action, target, note, location).
  • Enums are passed and stored as strings (readable in SQL).
  • Schema: 15 tables:
    • setup: Categories, Manufacturers, Suppliers, Locations, Departments, StatusLabels, AssetModels;
    • assets: Assets, Maintenances, AssetRequests;
    • licences: Licenses, LicenseSeats;
    • stock: StockItems, StockAssignments;
    • History.
    Plus the view vw_Assets and 34 procedures named PRO_AMS_<AREA>_<ACTION>.
  • Initialisation (development, AutoMigrate):
    • create the database if missing;
    • run 001_ams_schema.sql once (only when dbo.Assets does not exist);
    • always re-run 002_ams_procedures.sql (CREATE OR ALTER), split on GO;
    • if DemoTenantId is set and the database is empty, write demo data through the same procedures.

11In-house building blocks (L-43, L-44)

11.1 VMM.Mediator

  • Contracts: IRequest<T>, IRequestHandler<TReq,TRes>, IPipelineBehavior<TReq,TRes>, ISender / IPublisher / IMediator, INotificationHandler<T>, Unit.
  • Send:
    • resolves the handler and all behaviours for the request type from DI;
    • behaviours wrap the handler in registration order (first registered = outermost);
    • the generic pipeline per request type is built once and cached, so no reflection runs per call;
    • a missing handler raises HandlerNotFoundException.
  • Publish: runs every INotificationHandler<T> of the event's type and of its base classes, in order; no handler is fine.
  • Registration: AddMediator(cfg => cfg.RegisterServicesFromAssembly(..).AddOpenBehavior(..)) scans assemblies for handlers.

11.2 VMM.Mapper

  • Profiles: a MapperProfile declares CreateMap<TSource,TDest>(), with ForMember, Ignore, ConstructUsing and ReverseMap.
  • Plan per map, compiled once:
    • pick a factory: the given factory, else a parameterless constructor, else the public constructor with the most parameters that can all be filled (records);
    • then assign the writable properties not set by the constructor;
    • getters are compiled expression trees.
  • Conversions: assignable types, nullable, enum ↔ string / number, IConvertible, nested maps, collections (List, array, IReadOnlyList…).
  • Validation: AssertConfigurationIsValid() lists every destination member nothing maps to, and every type that cannot be converted. AddObjectMapper(assemblies) runs it at start-up.
